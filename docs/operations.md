# SwarmGram — эксплуатация и восстановление

## Адреса

- HTTP: `http://150.251.143.212:3000` / `http://swarmgram.is-a.dev`
- HTTPS (для Web Serial и безопасного контекста):
  `https://swarmgram.is-a.dev` (после выпуска сертификата),
  резервный `https://150-251-143-212.nip.io:3443`
- Hub API: `https://api.swarmgram.is-a.dev` (внутри web — `/api`)

HTTPS использует сертификат Let's Encrypt на `nip.io` + `is-a.dev`. Продление —
`/etc/cron.d/certbot-swarmgram`, сертификат копируется в
`/opt/swarmgram/certs` и nginx перезагружается. Ручной выпуск:
`/opt/swarmgram/scripts/issue-ssl.sh`.

> Прошивка модуля из браузера работает только на HTTPS-адресе или
> `localhost`: Web Serial недоступен в незащищённом контексте.

## Ключи шифрования (критично)

- Ключи server-чатов лежат в `chat_key_versions.key_enc` и зашифрованы
  `HUB_KEY_SECRET` (AES-256-GCM).
- `HUB_KEY_SECRET` **обязан** передаваться в контейнер Hub (см.
  `docker-compose.hub.yml`). Отсутствие секрета — ошибка конфигурации.
- При старте Hub пишет в лог `key_material_check`:
  `{"total":N,"ok":N,"failed":0}`. Если `failed > 0` — секрет не совпадает
  с тем, которым создавались ключи; восстановите `.env` из бэкапа.
- Ротация: `HUB_KEY_SECRET_OLD` (старые) + `HUB_KEY_SECRET` (новые), затем
  перезапуск. Не удаляйте старый, пока не перешифрованы все версии.
- `GET /v1/chats/:id/key` при проблеме возвращает `503 key_unavailable`,
  а не 500; клиент не должен показывать ложное «Зашифрованное сообщение».

## Резервные копии

- Скрипт: `/opt/swarmgram/scripts/backup-hub.sh`
- Cron: каждые 6 часов (`15 */6 * * *`)
- В архиве: `pg_dump` (включая `chat_key_versions`, `account_chat_keys`,
  `chat_keys`, `key_backups`, медиа-объекты) + `.env` с `HUB_KEY_SECRET` +
  compose.
- Шифрование: AES-256-CBC, пароль `/root/.swarmgram-backup.pass`.
  **Пароль храните вне сервера.**
- Проверка восстановлением выполняется вручную/по чек-листу:
  `pg_restore` в отдельную БД и сверка количества ключей/сообщений.
- Последняя копия складывается в `backups/` OneDrive (зашифрованная).
- Подробности: `backups/README.md`.

## Сессии и соединение

- Access-token живёт ~15 минут; клиент автоматически вызывает
  `/v1/auth/refresh` (single-flight) и повторяет 401-запрос.
- WebSocket переподключается с backoff 2→30 с, обновляет токен перед
  открытием, догоняет пропущенные события после reconnect.
- При `online`/возврате вкладки — немедленный reconnect.

## Модули

- Единая глобальная сеть для всех модулей: `SG-MESH` (скрытая), канал 11,
  LoRa 869.525 МГц / SF9 / BW125, Wi-Fi hops 14, LoRa hops 12. Параметры
  хранятся в singleton `mesh_config`; клиент их не настраивает.
- `hardware_id` = `esp32-<MAC>` из eFuse: не меняется при перепрошивке.
- `public_id` — 8 цифр, FNV-1a 32 от hardwareId `% 100000000`. Показывается
  пользователю, по нему добавляют ретранслятор/шлюз.
- Прошитый модуль до привязки принадлежит скрытому `system_modules`.
  `POST /v1/modules/register` (без пользовательского токена) создаёт/обновляет
  запись и выдаёт module-токен; `pair`/`claim` переводят владельца на аккаунт.
- При перепривязке у старого владельца остаётся shadow-запись
  «Был привязан на другом устройстве» с «Удалить» и «Это не я».
- Статус: gateway/repeater online при heartbeat < 150 с; wearable — только
  при `attached` (BLE/USB) и heartbeat < 90 с. Шлюз также обновляет
  `last_seen` модулей, которых видит в mesh (gossip).
- Shadow-запись автоматически скрывается, если модуль вернулся к прежнему
  владельцу.
- Прошивка: merged.bin, раздел `min_spiffs` (1.9 МБ app, OTA сохраняется).
  Wi-Fi часть работает через AP+STA mesh со скрытым `SG-MESH` и UDP-флудингом;
  пакеты мостятся между Wi-Fi и LoRa на каждом узле с обеими средами.
  Крупные конверты режутся на LoRa-фрагменты 150 Б × до 16 и собираются по
  `packetId`. Полный ESP-WIFI-MESH-путь остаётся за флагом `SG_USE_ESP_MESH`
  и требует core 3.x + отладки на железе.
- **Core 3.3.12 установлен**, доступны C3, ESP32 Lite и S3 (4 МБ), сборка
  `min_spiffs`. Для длинных сборок Hub/builder ждут до ~20 минут, а build-path
  на плату кэширует ядро между сборками.
- **Гибридная связь**: при отсутствии интернета клиент отправляет сообщение
  через подключённый модуль; при наличии шлюза API-запросы (поиск, чаты,
  история, отправка) идут через **зашифрованный relay-туннель**. Hub выдаёт
  устройству `meshRelayKey` при входе; шлюз видит только blob, не токен и не
  содержимое. Медиа через шлюз — только превью ≤64 КБ.
- В шапке чата и навигации отображается режим связи: интернет / через шлюз /
  модульная сеть. Presence профиля (username/publicId) передаётся по mesh.
- P2P без сервера работает при наличии локального ключа чата; полноценный
  обмен временными ключами для новых обычных чатов и серверное перешифрование
  ещё не завершены (см. roadmap).
- Мобильные приложения: BLE через `react-native-ble-plx` (нужна native
  сборка, не Expo Go). iOS Safari не поддерживает Web Bluetooth/USB;
  на iOS только native BLE.
- Клиент автоматически подхватывает ранее подключённый модуль при запуске
  (Web Serial `getPorts()` / BLE scan по service `a5c0`).

## Прошивка

- Сборщик: профиль `firmware`, только `esp32c3` (диск 10 ГБ).
- Сборка возвращает **merged.bin** (пишется с `0x0`). Старые app-only
  сборки помечены `merged=false` и не прошиваются из браузера.
- Браузер: Chrome/Edge на HTTPS, `navigator.serial`, esptool-js.
- После записи клиент читает MAC и автоматически привязывает модуль.
- Добавление плат: `ESP32_BOARDS=esp32c3,esp32` (нужно ~500 МБ на плату)
  и перезапуск контейнера сборщика.

## Быстрая диагностика

```bash
curl -s localhost:8080/health
docker exec swarmgram-firmware curl -s localhost:8090/health
docker logs swarmgram-hub 2>&1 | grep -E 'key_material_check|error' | tail
df -h /                      # свободно должно быть > 300 МБ
docker ps --format '{{.Names}} {{.Status}}'
```
