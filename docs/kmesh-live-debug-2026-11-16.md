# КМesh: итоги живой отладки 16.11.2026

## Подтверждено на устройстве (Android C17 Pro, модуль ESP32-C3 8F6:0A:11:B1:1C)

| Что | Результат |
| --- | --- |
| Скан BLE находит модуль по имени `KL-*` | да (`scan fallback: 1`) |
| Подключение и handshake INFO | да (`info esp32-e8f60a11b11c role=wearable`) |
| Автоподключение к своему модулю после перезапуска | да (`openKnown ... match=1`) |
| Карточка модуля на странице «Модули» | да (локальная карточка + серверная запись) |
| Капсула «Кластер офлайн» при подключённом модуле без шлюза | да |
| Текст сообщения при офлайне не превращается в замок | да («kmesh-offline-1», «kmesh-3» с часами) |
| Hub хранит KMesh-архив без потери шифртекста | да (header.ciphertextB64 + nonce + clientId) |

## Найденные и исправленные причины

1. **BLE-подключение не доходило до INFO.** Прошивка отдаёт длинный INFO
   (300+ байт) одним залпом; очередь notify в Arduino BLE переполнялась после
   1–2 пакетов, и клиент не собирал кадр. Теперь notify отправляются с паузой
   28 мс, INFO повторяется после HELLO.
2. **Приложение закрывало уже установленное соединение.** Сохранённый
   `hardwareId` был в старом формате (`esp32-<node8>`), новый — `esp32-<MAC12>`.
   `openKnown()` считал модуль «чужим» и рвал связь. Теперь сверка идёт по
   `mod6` из BLE-имени.
3. **`hardwareId` не проходил валидацию Hub.** `/kmesh/v1/modules/claim` ждёт
   MAC из 12 hex; прошивка отдавала 8 hex. Исправлено: `esp32-<12 hex MAC>`.
4. **Сообщение в офлайне становилось «Зашифрованным».** Без сети ключ
   серверного чата не получить, `encryptForChat` падал, а `localFallback`
   терял текст. Теперь: текст уходит через KMesh_v1 до шифрования серверного
   чата, а fallback сохраняет текст.
5. **Архив KMesh не расшифровывался.** Сообщения без `objectId` считались
   системными. Теперь расшифровываются из `header.ciphertextB64`, а `clientId`
   склеивает оптимистичное сообщение с архивным (Hub обновляет header при
   повторной синхронизации).
6. **Uplink без маршрута до шлюза терялся.** Роутер ставил пакет в pending и
   ждал RREP. Теперь при неизвестном маршруте пакет для `ANY_GATEWAY`
   отправляется широковещательно — шлюз в одном хопе его подхватывает.

## Что осталось

- **Wearable не подтверждает маршрут до шлюза** (`gateway=false` в INFO), хотя
  шлюз слышит его presence (RSSI −23…−38). Нужна отдельная отладка приёма
  beacon на C3 при активном BLE (coexistence) — вероятно, модуль пропускает
  beacon-пакеты. Поэтому капсула честно показывает «Кластер офлайн».
- **Мобильный шлюз в приложении не включён**: `INET_STATUS` и `PROXY_UP`
  реализованы в `kmesh/v1/service.ts`, но не подключены к нативному
  `ModuleProvider`. Это следующий шаг, чтобы KMesh работал через интернет
  телефона без ESP32-шлюза.

## Диагностика

`adb logcat | findstr "\[ble\]"` — скан, connect, приём чанков, INFO/таймаут,
`openKnown` match. Прошивка дополнительно пишет `[kmesh] beacon/presence` в UART.
