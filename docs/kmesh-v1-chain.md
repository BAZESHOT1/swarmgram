# KMesh_v1: сквозная цепочка передачи данных

Документ фиксирует найденные разрывы и внесённые исправления в цепочке
`приложение → BLE → носимый модуль → ESP-NOW → шлюз → Hub → обратно`.

## Найденные причины

### 1. Сборщик собирал устаревшую прошивку

- `services/firmware-builder/server.mjs` выбирал `klinto_module_v2.ino`
  по умолчанию (`kmesh.v1 = false`), поэтому в устройства попадал старый
  стек `mesh_v2` с тегами `[lora] frag`, `[http] relay`, `type=7`.
- Hub (`POST /v1/firmware/build`) полностью вырезал поле `kmesh` из
  конфигурации сборки и никогда не подставлял `TEMP_MESH_KEY`.
- Итог: в прошивке не было общего транспортного ключа, а старый роутер
  продолжал ретранслировать пакеты без ограничения темпа.

Исправлено:

- KMesh_v1 теперь выбирается по умолчанию (`kmesh.v1` = `true`);
  `KL_MESH_V2` принудительно `0`.
- Hub валидирует `kmesh`, всегда собирает `v1` и подставляет
  `TEMP_MESH_KEY` из окружения (64 hex). Без ключа сборка возвращает
  понятную ошибку, а не «тихо» собирает нерабочую прошивку.
- `TEMP_MESH_KEY` добавлен в `.env.example` и `docker-compose.hub.yml`.

### 2. Эфирный шторм и аппаратные ребуты

- У драйвера ESP-NOW не было паузы между кадрами: `sendPacket()` отправлял
  сразу, очередь была 8 кадров без повторов.
- Маяк шлюза уходил раз в 90 секунд, скан каналов у носимого модуля стоял
  на 450 мс, а периодический рескан каждые 2.5 минуты сбрасывал маршруты.

Исправлено в `klinto_espnow.*` и `klinto_cell.*`:

- жёсткий TX pacing: не чаще одного кадра в **25 мс**;
- очередь **16** кадров, **3** попытки на кадр, затем кадр выбрасывается;
- шлюз рассылает `GW_BEACON` каждые **5 с** и кладёт в payload свой
  `wifi_channel`;
- носимый модуль сканирует каналы `1..13` по **120 мс**, ловит маяк и
  фиксируется ровно на канале шлюза;
- при смене канала AP шлюза модуль переезжает сразу, без ожидания таймаута;
- здоровая сота больше не пересканируется по таймеру; поиск запускается
  только при потере маяков (20 с) или слабом RSSI;
- канал `6`/`1` нигде не перебивает канал шлюза: стартовый канал — только
  подсказка до первого маяка.

### 3. Шлюз умел только MQTT, а брокера в стеке нет

- `KlintoNode` инициализировал `MqttTlsTransport`, но в `docker-compose`
  нет ни Mosquitto, ни EMQX. Любой uplink молча терялся.

Исправлено:

- добавлен `HttpGatewayTransport` (`klinto_http_gateway.*`):
  `POST /v1/kmesh/v1/relay?kind=archive|presence` с заголовком
  `x-kmesh-key`, плюс короткий поллинг
  `GET /v1/kmesh/v1/downlink?gateway_id=...&since=...` раз в **1.8 с**;
- в Hub добавлены `/v1/kmesh/v1/relay` и `/v1/kmesh/v1/downlink`,
  миграция `040_kmesh_v1_downlink.sql`;
- на каждый принятый архив сервер ставит ACK в очередь downlink, шлюз
  превращает его в `KL_TYPE_ACK` и отправляет на носимый модуль;
- шлюз больше не зависит от наличия MQTT-брокера.

### 4. iOS BLE: подключение падало до handshake

- `BleKMeshV1Link` сканировал по префиксу `Klinto-`, хотя модули
  называются `KL-<USER8>-<MOD6>`;
- `connectToDevice()` вызывался без предварительного `stopDeviceScan()`;
- не было mutex и ретраев; префикс владельца читался уже после скана.

Исправлено:

- префикс по умолчанию `KL-`, берётся из `loadCachedIdentity()` до скана;
- перед подключением — `stopDeviceScan()` и пауза 250 мс;
- все подключения идут через общую очередь (`withConnectLock`), до 2 попыток;
- имя сравнивается без учёта регистра по `device.name` и `device.localName`;
- в `KlintoClientBridge` добавлена совместимость со старым кадром `A5 5A`
  (HELLO/PING → INFO/PONG), чтобы текущая мобильная сборка могла
  подключиться к новой прошивке и получить `INFO`.

## Трассировка

После прошивки в Serial выводятся четыре метки:

```
[TRACE 1/4] BLE->NODE: recv RPC cmd=1 len=.. msg_uuid=........ dst=...
[TRACE 2/4] ESPNOW->GW: rx packet msg_uuid=... src=...
[TRACE 3/4] GW->HUB: uplink ok status=200
[TRACE 4/4] HUB->GW->NODE->BLE: delivered msg_uuid=...
```

Если цепочка рвётся, отсутствие следующей метки сразу показывает стык.

## OTA

`fw_build` поднят до **141**. Образы собраны отдельно для ролей
`wearable` и `gateway`. Публикация в OTA намеренно не выполнена:
текущий OTA-ключ — только `chip + build`, а роль зашита в образ
(`KL_ROLE`). Если выложить один образ на всех, шлюз получит прошивку
ведомого (и наоборот). Для безопасного OTA нужен ключ `chip + role + build`;
до этого шлюз и носимый модуль прошиваются образом своей роли.
