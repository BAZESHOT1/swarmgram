# kMesh: сеть и обмен сообщениями

kMesh — радиосеть из ESP32-модулей, по которой телефоны обмениваются сообщениями без интернета и с ним (через шлюзы).

## Топология

- **Кластер** задаёт шлюз (его канал и `gateway_id`). Модули кластера слышат друг друга по ESP-NOW (Wi‑Fi LR) и/или LoRa.
- Шлюз выходит в Hub по Wi‑Fi (HTTP). Носимый модуль может работать как **мобильный шлюз**: телефон с интернетом пересылает uplink в Hub (`/kmesh/v1/mobile/*`).
- Модули на границе слышат соседние кластеры; карта кластера на Hub строится из `kmesh_v1_links`.

## Кадры клиент↔модуль

`magic 0x53 0x47`, версия 3, `type`, `flags`, `seq u16`, `len u16`, payload, `crc16`. Основные типы: HELLO/INFO, SET_CONFIG/CONFIG, RPC_UP (телефон→сеть), RPC_DOWN (сеть→телефон).

Операции RPC (`RpcOp`): `SEND_TEXT 0x01`, `SEARCH 0x08/0x09`, `FEED 0x0a/0x0b`, `HISTORY 0x0c/0x0d`, `SEND_ENVELOPE 0x0e`, `CHAT_KEY_REQ/RESP 0x0f/0x10`, `LOCAL_SEARCH_REQ/RESP 0x20/0x21`. Адреса: `ANY_GATEWAY_ID=1`, `BROADCAST_ID=0xffffffff`. Флаги пакета: `NEED_ACK 0x01`, `TO_INTERNET 0x02`, `NEED_CLOUD_ARCHIVE 0x20`.

## Выбор ключа при отправке

| Ситуация | Что используется |
| --- | --- |
| Секретный чат | Только E2E-ключи, серверный ключ не используется |
| Есть шлюз/Hub | Серверный ключ чата (запрашивается `CHAT_KEY_REQ` через шлюз и кэшируется) |
| Нет Hub, ключ кэширован | Закэшированный серверный ключ |
| Нет Hub, кэша нет | **Ключ пары**: `HKDF(sha256, ECDH(мой P-256, аккаунт-ключ собеседника)[1..32], salt=chatId, info='klinto-kmesh-pair-v1')` |
| Публичный канал | Допускается открытый текст; во всех остальных случаях открытый текст запрещён — сообщение остаётся в outbox |

Шифрование — AES-GCM, полезная нагрузка — JSON `{text}` (для пары — с `ts` и подписью, если укладывается в 150 символов).

## Доставка и синхронизация

- Сообщения по паре помечаются `kind: text:pair`; Hub их пересылает, но не хранит как есть.
- Получатель может **выгрузить копию** на Hub (`/kmesh/v1/relay-sync`), если автор не вышел в сеть: подпись автора `ECDSA P-256 над sha256("klinto-relay-v1|msgUuid|chatId|ts|sha256hex(text)")` проверяется по `devices.identity_pub`; Hub перешифровывает серверным ключом.
- Статусы модуля: отправлено → доставлено → **синхронизировано с Hub** (ACK с `payload[8]=1`).
- Downlink: шлюз опрашивает Hub (`/kmesh/v1/downlink`, до 8 записей за раз, без курсора) и раздаёт по mesh.
- Группы и каналы без шлюза рассылаются broadcast внутри кластера.

## Поиск без Hub

`LOCAL_SEARCH_REQ` рассылается broadcast в кластере (+ ближайшие соседние); телефоны отвечают своим @username и публичными группами/каналами. С Hub одновременно работает серверный поиск.

## Карта кластера и presence

Модуль отдаёт список «кого слышу» (id, RSSI, флаги: 1 — шлюз, 2 — LoRa) — в INFO (телефону) и в presence (шлюзу → Hub, после 19 байт телеметрии: счётчик + записи по 6 байт). Hub хранит связи в `kmesh_v1_links` и отдаёт `GET /v1/kmesh/v1/topology` — узлы, связи, шлюзы с доступом к Hub, соседние кластеры.

## Известные ограничения

- Подпись для relay-sync есть только у коротких текстов.
- Копию на Hub выгружает получатель только при наличии у него интернета.
- Временный общий ключ можно подделать на уровне модуля (план: ключи по узлам).
- LoRa на RadioLib 8 собирается, но на железе ещё не проверена.
