# Hub: серверная логика

Hub — Fastify-приложение (`services/hub/src`). Точка входа `index.ts`: подключает БД (`db.ts`, миграции из `sql/` применяются по порядку), регистрирует маршруты, WebSocket (`realtime.ts`) и фоновые задачи.

## Фоновые задачи

| Модуль | Что делает |
| --- | --- |
| `monitor.ts` | Следит за heartbeat узлов (degraded/offline), публичный ping, суточные кредиты |
| `replicator.ts` | Восстанавливает недостающие копии фрагментов и проверяет SHA-256 |
| `push.ts` | Воркер push-уведомлений (FCM) |
| `drain.ts` | Вывод узлов из эксплуатации |
| `kmeshDownlink.ts` / `kmeshRpc.ts` | Очередь доставки сообщений на шлюзы kMesh и разбор RPC от модулей |
| `ota.ts` | Планы и патчи OTA-обновлений модулей |

## Маршруты (`src/routes`)

| Файл | Префикс / область |
| --- | --- |
| `auth.ts` | Регистрация, вход, подтверждение по email, refresh токена |
| `users.ts`, `devices.ts` | Профиль (`/me`), username (смена раз в 90 дней), устройства и prekeys |
| `accountKeys.ts`, `keys.ts` | Публичные ключи аккаунта (ECDH P-256), резерв ключей |
| `chats.ts`, `channels.ts`, `messages.ts` | Чаты, группы, каналы, сообщения, реакции, просмотры, приглашения |
| `objects.ts`, `nodes.ts` | Хранение шифртекстов: `objects/init` → 3 реплики → `commit`; регистрация и heartbeat узлов |
| `modules.ts` | Модули аккаунта (устаревшая серверная модель), привязка, блокировка, передача, OTA-задачи |
| `kmeshV1.ts` | Всё про kMesh_v1: presence, relay, архив, поиск, лента, downlink, топология, модули по MAC, OTA |
| `meshNetwork.ts`, `mesh.ts`, `offlineSync.ts` | Глобальная mesh-конфигурация, офлайн-синхронизация, mesh-реестр |
| `firmware.ts` | Сборка прошивок: валидация конфига, очередь, статус, скачивание, `GET /firmware/releases` |
| `admin.ts` | Админ-API: аккаунты, узлы, модули, чаты, жалобы, аудит, **документация (`/admin/docs`)** |
| `notifications.ts`, `stats.ts`, `network.ts` | Push-настройки, статистика, состояние сети |

Все пути идут под префиксом `/v1` (через nginx — `/api/v1`).

## Аутентификация

- Access-токен ~15 минут, refresh — отдельно; клиент автоматически обновляет (single-flight) и повторяет запрос.
- `requireAuth()` — пользовательский JWT. `requireAdmin()` — пользователь с `users.role='admin'` либо заголовок `x-admin-token`.
- `rateLimit(key, n, windowMs)` — простые лимиты (например, 5 сборок прошивки в час на пользователя).

## Realtime

WebSocket `/ws?token=<access>`: Hub публикует события `message`, статусы модулей и т.д. Клиент переподключается с backoff 2→30 с и догоняет пропущенное.

## Шифрование на сервере

- Hub не расшифровывает E2E-чаты, но для **server-чатов** хранит ключи (`chat_key_versions.key_enc`, зашифрованы `HUB_KEY_SECRET`) — это нужно, чтобы шлюзы и kMesh-клиенты без прямых ключей могли шифровать/читать сообщения.
- `POST /kmesh/v1/relay-sync` принимает копию kMesh-сообщения от любого участника чата: проверяет подпись автора (ECDSA P-256 по `devices.identity_pub`), расшифровывает серверным ключом, сверяет хеш текста и записывает сообщение от имени автора.

## Сборка прошивок

`POST /firmware/build` валидирует конфиг (`validateConfig`: плата, роль, связь, LoRa-чип и пины, батарея, имя модуля), подставляет глобальные mesh-параметры из `mesh_config`, пишет строку в `firmware_builds` и в фоне отправляет запрос сборщику (`FIRMWARE_BUILDER_URL`). Готовый `.bin` лежит на диске Hub; после успеха обновляется `firmware_releases` (последняя версия по плате в формате `<версия>/<сборка>`, например `1.4/176` — именно так модуль сообщает свою прошивку, по этому сравнению клиент показывает «обновление»).
