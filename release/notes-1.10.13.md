# Klinto 1.10.13 — мобильный шлюз и стабильный маршрут до шлюза

Дата: 16 ноября 2026 года.

## 1. Почему капсула писала «Кластер офлайн»

- Periodic rescan вызывал `apply()` тем же каналом, а обработчик канала
  сбрасывал маршруты и `gw_`. Маршрут до шлюза жил до следующего beacon.
  Теперь `apply()` и `on_channel_changed()` не трогают маршруты, если канал
  не изменился.
- Минимальный интервал GW_BEACON снижен с 30 с до 5 с (по умолчанию 5 с):
  после любого сброса маршрут восстанавливается за секунды, а не за полминуты.
- Для C3/C6 (BLE + ESP-NOW на одном радио) отключён modem sleep Wi-Fi
  (`WiFi.setSleep(false)`, `WIFI_PS_NONE`) — beacon/RREP больше не пропускаются.
- INFO теперь содержит диагностику: `bcn` (услышано beacon'ов), `gwAge`
  (возраст маршрута), `ch`, `mobile`. Её видно в `adb logcat` по строке
  `[ble] v1 info ...`.

## 2. Мобильный шлюз (телефон вместо ESP32-шлюза)

- Приложение отправляет `INET_STATUS` каждые 15 с (и сразу при смене сети).
- Прошивка при наличии интернета у телефона включает mobile-gateway и шлёт
  uplink в BLE-клиент (`PROXY_UP`).
- Приложение пересылает пакеты в Hub: `POST /v1/kmesh/v1/mobile/relay`
  (аутентификация пользователем, только для привязанного узла).
- Downlink: приложение опрашивает `GET /v1/kmesh/v1/mobile/downlink` каждые
  5 с и отдаёт пакеты модулю (`PROXY_DOWN`).
- INFO отдаёт `gateway=true` и при mobile-gateway, поэтому капсула скрывается,
  когда кластер реально имеет доступ к Hub.

## 3. Все ESP32 с BLE

- Сборщик: BLE включается для wearable и repeater на `esp32`, `esp32c3`,
  `esp32s3`, `esp32c6`; для шлюза — по флагу `ble: true`.
- Добавлена плата `esp32s2`: она **без Bluetooth**, сборка с BLE для неё
  возвращает понятную ошибку `ble_not_supported:esp32s2`, а как узел без BLE
  плата поддерживается.
- BLE-транспорт и прошивка используют общий для всех вариантов стек Arduino
  BLE; отдельного кода под конкретный чип нет.
